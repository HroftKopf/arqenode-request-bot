## 4. Значимые архитектурные решения

### 4.1. Стабильные коды статусов и миграция v1→v2

Русские подписи в `requests.status` заменены кодами. Миграция пересоздаёт
таблицу `requests` с `DEFAULT 'new'` и `CHECK`, сохраняя `id`, `user_id`,
`category`, `description`, `created_at`. `PRAGMA foreign_keys=OFF`
используется только на время транзакции, после — включается и выполняется
`PRAGMA foreign_key_check`. Неизвестные статусы **блокируют** миграцию и
откатывают её: данные не теряются, администратор должен разобраться вручную.

### 4.2. WAL и транзакции

`journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=10000`. Соединение
работает в autocommit (`isolation_level=None`), записи — явный
`BEGIN IMMEDIATE`. Это сохраняет защиту от гонок двух администраторов и
уменьшает блокировки читателей. Для смены статуса/отмены/редактирования
используется транзакция «прочитать → проверить → записать», а не отдельные
запросы.

### 4.3. Снимок истории

Пагинация использует `max_id` (ID последнего сообщения на момент открытия
истории). Все страницы фильтруются по `id <= max_id`, поэтому новые сообщения
не сдвигают страницы. Старый 4-частный callback поддержан для совместимости;
новый 5-частный содержит `max_id`. Callback-data остаётся < 64 байт.

### 4.4. Rate limiting

In-memory скользящее окно по ключу `(user_id, action)`, отдельные правила для
операций. Не использован Redis: бот работает одним polling-процессом; это
сознательно не усложняет архитектуру. Ограничение состояния по числу ключей
защищает память. После рестарта окна сбрасываются — это документированное
ограничение.

### 4.5. Уведомления

Повторяются только 429 и сетевые/серверные сбои (до 3 попыток, задержка
0.5–5 с). 403/400 считаются постоянными. Логи содержат получателя, тип ошибки
и retry-after, но не текст сообщения и не токен. Если клиент не получил
уведомление о смене статуса, администратор получает предупреждение.

### 4.6. FSM

`MemoryStorage` оставлен: один процесс, нет внешней инфраструктуры; перенос в
Redis не даёт пользы при текущем запуске и добавил бы зависимость/точку отказа.
Корректность отмены, stale-state, повторных команд и изоляции пользователей
покрыта тестами. Ограничение сброса при рестарте указано в README и отчёте.

### 4.7. Аудит

`admin_actions` заполняется в той же транзакции, что и статус/ответ, поэтому
действие и аудит не расходятся. Пишутся `admin_id`, тип операции, `request_id`,
переход статусов и время. Тексты сообщений и персональные данные туда не
попадают.

## 8. Оставшиеся ограничения и риски

1. **Токен всё ещё хранится на диске** в `.env` (и в защищённой копии
   `.env.backup`). Это нормально для polling-бота, но требует ротации при
   подозрении на утечку. Рекомендуется удалить `.env.backup` после ротации.
2. **Старые бэкапы и старый монолит** (`main.py.backup`, `requests.db.backup`,
   `.env.backup`) сохранены по требованию «не удалять». Они защищены правами,
   но содержат устаревшие PII/ID. Рекомендуется архивировать/удалить вручную
   после подтверждения.
3. **FSM в памяти**: незавершённый ввод сбрасывается при рестарте. Для
   нескольких процессов потребуется Redis/БД-storage — это отдельное решение.
4. **Rate limiting в памяти**: не распределён между процессами; при переходе на
   несколько воркеров нужен общий store.
5. **SQLite/WAL**: на сетевых ФС WAL может быть небезопасен; приложение
   рассчитано на локальный диск. Бэкапы делать только через
   `sqlite3.Connection.backup` или при остановленном боте.
6. **Нет внешнего мониторинга/алертинга** ошибок доставки и БД; логи ротируются,
   но не отправляются в систему мониторинга.
7. **Нет git-репозитория**: `.gitignore` готов, но история изменений и
   автоматическая проверка секретов в CI не настроены. Рекомендуется
   `git init`, первый коммит после `git status`/secret-scan.
8. **Покрытие не 100%**: не покрыты rollback-ветки и импортный fail-closed
   путь (проверен отдельно). Это не скрывает функциональные сценарии.
9. **Бот не запускался и не деплоился** в рамках задачи; проверка была
   локальной, на временных БД/копиях. Production-запуск требует отдельного
   smoke-теста с реальным токеном.
10. **Аудит охватывает статусы и ответы администраторов**, но не чтение
    панели/списков; для полного compliance может потребоваться расширение.

## 9. Безопасный запуск обновлённой версии

1. Остановите старый процесс (не допускайте двух polling на один токен).
2. Убедитесь, что бэкап существует и защищён:
   `backups/20261123T203713Z/` (`700`, файлы `600`).
3. Проверьте миграцию на копии (команды из README):
   ```bash
   cp requests.db /tmp/requests-check.db
   DATABASE_PATH=/tmp/requests-check.db python -c \
     "import asyncio, database; asyncio.run(database.init_db())"
   sqlite3 /tmp/requests-check.db "PRAGMA user_version; PRAGMA integrity_check;"
   ```
   Ожидается `3` и `ok`; число заявок/сообщений не изменилось.
4. Установите зависимости:
   ```bash
   source .venv/bin/activate
   python -m pip install -r requirements.txt
   ```
5. Проверьте права: `chmod 600 .env requests.db`, `chmod 700 backups`.
6. Запустите `python main.py`, проверьте `bot.log` и отправьте тестовую заявку
   с тестового клиента.
7. При ошибке миграции бот завершится с понятным сообщением; данные останутся
   нетронутыми (транзакция откатывается). Восстановление — из бэкапа.

- Перевыпустить токен, если каталог/бэкап могли быть скопированы; удалить
  `.env.backup`/старые копии после ротации.
- Запускать под отдельным Unix-пользователем, `.env`/БД — `600`, каталог — `700`.
- Настроить systemd/healthcheck и автоперезапуск только одного экземпляра.
- Настроить регулярные проверенные бэкапы и политику хранения PII.
- Вынести логи/ошибки в мониторинг (без текстов сообщений и токена).
- При нескольких воркерах — Redis/БД для FSM и rate limiting.
- Добавить CI: `ruff check`, `unittest`, `coverage report --fail-under=80`,
  secret-scan.
- Для webhook — HTTPS/ reverse proxy; текущий polling не требует веб-сервера.
- Периодически проверять `PRAGMA integrity_check` и тестировать восстановление.
